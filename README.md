# Ghost in the Shell  Hackathon Solution

# **Аанализ графа денежных переводов**  

Репозиторий содержит детерминированный пайплайн для расследовательского анализа графа переводов в KZT.<br>Он объединяет данные об участниках, агрегированных связях и отдельных транзакциях, чтобы:
 - определить роль каждого узла в цепочке движения средств;
 - найти сообщества связанных участников;
 - сформировать список узлов, которые стоит проверить в первую очередь.
<br>
Пайплайн не использует ML или LLM: результаты воспроизводимы при одинаковых входных данных. 

## Что делает пайплайн
 - Строит ориентированный граф из агрегированных переводов.
 - Для каждого узла определяет количество независимых исходных (seed) цепочек, которые к нему пришли.
 - Считает входящие и исходящие суммы, число контрагентов, временную задержку между первым входящим и исходящим переводом, а также betweenness centrality.
 - Разбивает неориентированный граф на сообщества алгоритмом Louvain с фиксированным seed 42.
 - Назначает роль, оценку уверенности и приоритет для ручной проверки. 

## Требования:
 - Python 3.10 или новее;
 - зависимости из requirements.txt;
 - входные файлы Parquet, уже включённые в репозиторий.

## Входные данные
Файл	        Назначение	Используемые поля<br>
nodes.parquet	Узлы графа<br>	gid, is_seed, depth
edges.parquet	Агрегированные связи между узлами<br>	src, dst, sum_kzt, n_tx, depth
transactions.parquet	Отдельные переводы для временного анализа	src, dst, date

<br>Где:<br>
gid, src, dst — идентификаторы участников;<br>
is_seed — признак исходного узла известной цепочки;<br>
depth — глубина узла или связи в обходе графа;<br>
sum_kzt — сумма агрегированных переводов в тенге;<br>
n_tx — число переводов, вошедших в агрегированную связь;<br>
date — дата перевода. 

## Роли узлов

 - coordinator — Узел-мост из верхних 10% по betweenness centrality, имеющий не менее трёх входящих и трёх исходящих связей.<br>
 - consolidator — Получает средства как минимум из трёх независимых seed-цепочек или от трёх и более плательщиков.<br>
 - distributor — Имеет не менее пяти исходящих и не более двух входящих связей.<br>
 - transit — Почти полностью передаёт полученные средства дальше (out / in от 0.8 до 1.2) не позднее чем через три дня.<br>
 - terminal — Имеет входящие, но не имеет исходящих переводов в графе. Для узла на глубине 4 оценка снижена: это может быть граница обхода.<br>
 - peripheral — Не соответствует правилам выше.<br>
* Правила применяются сверху вниз в указанном порядке. Поле role_score — эвристическая оценка уверенности в назначенной роли, а не вероятность.<br>

После успешного запуска будут созданы три CSV-файла.

nodes_roles.csv<br>
Поле	Описание<br>
gid	 — Идентификатор узла<br>
role — 	Назначенная роль<br>
role_score — 	Оценка уверенности в роли<br>
cluster_id	 — Идентификатор сообщества Louvain<br>
priority_score	 — Нормализованный приоритет ручной проверки от 0 до 1<br>
evidence	Краткое  — текстовое объяснение решения<br>
<br>
clusters.csv<br>
Поле	Описание<br>
cluster_id	 — Идентификатор кластера<br>
n_nodes	 — Число узлов в кластере<br>
n_seed	 — Число seed-узлов<br>
sum_kzt_internal — 	Внутренний оборот кластера в KZT<br>
top_gids	 — До пяти наиболее приоритетных узлов<br>

<br>
top_nodes.csv<br>
Поле	Описание<br>
rank — 	Место в списке<br>
gid — 	Идентификатор узла<br>
role	 — Назначенная роль<br>
priority_score	 — Приоритет ручной проверки<br>

Интерпретация  — результатов<br>
priority_score  — учитывает роль, уверенность классификации, число независимых seed-цепочек, число связей и признак seed-узла.<br>Его следует использовать для очередности проверки, а не как самостоятельное доказательство связи участников. <br>Гипотезы и роли требуют аналитической верификации с учётом внешнего контекста.
